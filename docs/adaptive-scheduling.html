Resource learning and adaptive admission

Contract

The queue measures the machine and each owned process group, learns conservative CPU and memory envelopes for recurring jobs, and can delay a job when its predicted demand does not fit current headroom. The operator controls the maximum number of concurrent jobs. Fixed scheduling remains the default, Learn only produces shadow decisions, and Adaptive explicitly enables resource-based admission. Changing mode never terminates an active job.

Workload identity

  • A workload family consists of the shared Git repository identity, logical command and repository-relative package or target. Linked worktree paths, branch names and commit hashes do not define the family. Unrelated repositories with the same basename stay separate. Separate clones are not automatically merged by remote URL.
  • Variants include meaningful arguments, resource-affecting worker flags, bounded script/configuration and dependency fingerprints, toolchain metadata, source revision and environment provenance. Related variants borrow conservative family evidence instead of losing all learning after a source change. Unknown argument semantics are preserved.
  • Optional AGENT_HEAVY_PROFILE names deliberately relate opaque or non-Git workloads. Their contents are hashed and never displayed by the resource API. Cache context is recorded separately; duration predictions remain conservative across observed contexts.

These identities are statistical grouping keys, not reproducible-build or whole-source content hashes. A bounded scan does not read every source file or dependency tree. The controller recomputes neither source nor command content while a job runs. Existing queued jobs without identities migrate from their private acknowledged payloads before admission; unidentified active jobs block new adaptive overlap conservatively.

Observation and learning

The resource controller is a separate per-user login service. Pueue continues to own jobs, independent of the caller and UI. Native Darwin counters provide host CPU intervals, available memory, pressure, swap rates and disk space. Each job's verified process group is sampled for simultaneous physical footprint and observed cumulative CPU and I/O counters. PID birth identities and repeated membership checks prevent attributing a reused process group to an older job. No new privileged service or Python runtime dependency is needed.

CPU-seconds describe total observed computation, while CPU core demand and peak memory inform overlap. Summing simultaneous worker footprints avoids adding unrelated lifetime peaks. Workers born and exited entirely between samples, or peaks entirely between samples, remain invisible; observed totals are lower bounds. Completeness means the required sampled intervals were available, not kernel-enforced lifetime accounting.

Execution start time is published with the ownership lease. A controller that first observes a job late, lacks its execution start, misses a sampling interval, or crosses sleep/clock discontinuities marks its learning history incomplete. Healthy current intervals can recover admission readiness without turning the earlier unobserved work into complete training evidence.

Private SQLite history retains bounded numeric run records and opaque workload identities. Predictions prefer the exact variant, then related family evidence, then a conservative prior. Exact variants need repeated comparable successful observations before lowering the cold-start envelope. Family transfers use an extra margin. Underestimates and peaks from failed or incomplete runs raise retained upper evidence. Old evidence gradually loses confidence. A collector restart, observation gap, cancellation or nonzero exit cannot establish that a job is cheap, and old observation timestamps are preserved across restarts.

Shadow and adaptive admission decisions are also retained in bounded private SQLite audit history, including numeric predictions and fixed explanation text. Unchanged decisions are coalesced without rewriting their original timestamp. These records support later comparison with measured outcomes without retaining command contents.

The controller adjusts learned resource envelopes within fixed operator constraints. It does not autonomously raise concurrency limits, reduce emergency reserves, change test-worker counts, or alter commands. Pair-specific interference models, phase forecasts, energy prices and monetary billing are outside this version; measured resource envelopes determine overlap.

Admission and ownership

Adaptive submissions are durable Stashed Pueue tasks. The controller checks current queue state, fresh host observations, memory pressure, swap rate, disk headroom, the operator ceiling and current owned work. A candidate reserves its predicted memory peak; an active job reserves potential growth above its current footprint. Current host usage is counted once. CPU reservations similarly account for observed activity and future demand.

Automatic starts require an expiring grant tied to the job token, boot and scheduling generation. Immediately before executing a command, the helper verifies the grant and current resource status under the existing private ownership lease lock. This check also enforces the latest parallel ceiling. Pending starts reserve capacity until their lease is acquired or the grant expires. Newly acquired but unsampled leases block further starts. Pressure, stale observations and controller failures revoke or invalidate pending automatic admission. Manual Start now records an explicit override.

Unfamiliar jobs run alone until comparable successful evidence accumulates. Resource-fitting backfill can use spare capacity behind a temporarily blocked job of equal priority, but higher-priority jobs retain precedence. An older waiting job reserves the next opportunity after a bounded wait, preventing starvation. An estimate exceeding the machine's budget produces an actionable explanation instead of an unexplained delay.

Recovery and operator controls

Missing or stale resource telemetry holds new adaptive starts. The UI preserves monitoring failure separately from queue connectivity, and Fixed and Learn only remain selectable. Returning to Fixed re-enqueues managed jobs through Pueue and preserves an intentionally paused queue. Existing force-start, cancellation, legacy-owner exclusion and daemon crash ownership rules remain in force. Suspending a process would not reclaim its memory, so adaptive admission does not use suspension as recovery.

The installer ships the resource modules and a separate resource-controller login entry without replacing or restarting a running queue daemon. Local development can run the controller against a deliberately isolated queue with agent-heavy scheduler; production installation starts it independently. Do not point test controllers at the operator's real queue.

Validation

Focused tests cover worktree identity and variants, sampled counter resets and process churn, censored learning, conservative estimates, bounded private storage, budget arithmetic, stale grants, generation changes, pressure recovery, concurrent lease observations, fairness, controller restart and mode transitions. Real-daemon acceptance uses private Pueue instances and simulated resource demand to exercise stashed admission, overlapping known jobs, lowering the ceiling, manual override, controller loss, queued-job migration and ordinary fixed scheduling. Native, browser, schema, API and installer regressions cover the visible controls and packaging. macOS CI runs on Intel and Apple Silicon.
