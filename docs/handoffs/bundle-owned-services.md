# Bundle-owned background services

## Scope and accepted behavior

The user authorized local implementation of explicit installation, read-only ordinary startup, and Apple's supported Service Management lifecycle after repeated SentinelOne quarantines on a different Mac. Source baseline: `ced25f439b10496f819a6237f5bd53942fbcb791`. This change does not authorize an affected-Mac repair, security exclusion, Apple submission, release or deployment.

Original incident evidence and the build-58/build-94 comparison are recorded in the [SentinelOne investigation](sentinelone-detection-investigation.md).

Requirements carried into implementation:

- Installation and upgrades perform setup explicitly. Opening an incomplete app shows instructions without rewriting files or automatically retrying recovery.
- Runnable helpers and launch definitions stay inside the signed owning app. Login uses the owning app's Service Management registration, without an `open -a` LaunchAgent.
- The daemon remains independent of the menu UI. Migration, replacement and removal require a drained queue before service changes; active work is preserved through refusal.
- User approval and current phone-access intent remain authoritative. Missing, malformed or uncertain ownership never permits a fallback registration or process kill.
- Pending installation identities remain authoritative across failure and retry. Completed identities cannot certify an incomplete installation.
- Apple Silicon and Intel packaging, signatures, quarantine, retained archives and queue history remain supported.
- Local source/fixture validation is separate from live Service Management, signed release and SentinelOne qualification.

## Layout and lifecycle

New packages declare the boolean `AgentQueueServiceManagement` marker. `AgentQueue`, `agent-heavy` and `agent-remote` live in `Contents/MacOS`. The three queue, resource-controller and optional phone-service definitions live in `Contents/Library/LaunchAgents` and use bundle-relative `BundleProgram` paths. The app's support payload retains metadata and documents without duplicate helper binaries. The outer installer retains its own controller payload.

The native `QueueServiceManagement` interface accepts fixed status/register/unregister operations for queue, resources, remote and login. It validates the owning bundle before constructing an adapter, reports approval states explicitly, propagates failures and waits for asynchronous unregister completion. The app handles these commands before starting AppKit. Ordinary app startup reads readiness and service status; installation/recovery requires an explicit installation workflow.

The dedicated replacement interface politely quits only a running menu app with the exact canonical target URL, bundle identifier and current-user ownership. It excludes the native caller and other copies, waits for exit, and refuses changed identity, denied termination or timeout without force-killing. Explicit payload replacement and removal invoke it after drain and before changing bundle custody. In-place `--setup` does not terminate the app owning setup. The final one-shot app open happens after durable completion; registering the main app as a login item alone does not open its UI immediately.

Apple's SDK states that changed helper code requires re-registration, unregister terminates a running helper, and the asynchronous completion callback is the safe point for re-registration. These requirements are the basis for the drain and completion gates, not a prediction about SentinelOne's detector. [Apple Service Management](https://developer.apple.com/documentation/servicemanagement/smappservice), [registration](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29), [unregister completion](https://developer.apple.com/documentation/servicemanagement/smappservice/unregister(completionhandler:)).

The Go installer performs bounded no-follow ownership reads, validates package identity/signatures, checks drain and service ownership, and rechecks under its installation/scheduling/remote locks. It retains the pending identity through app publication, native registration, readiness and remote adoption. `installation.json` records the canonical app location; malformed metadata cannot select the legacy path. Unmarked retained archives retain their existing behavior, but cannot overwrite an established managed installation.

Readiness validates the actual public `status --json` response (`queue`, `jobs`, `scheduler` and timestamp). Drain uses the independent daemon's private snapshot (`tasks` and `groups`). Tests must preserve this distinction instead of returning a private snapshot for the public command. Native commands have a 35-second outer limit around the bridge's 30-second completion limit, preserving time for startup and a diagnostic result.

Read-only native status is bounded separately at five seconds. Phone lifecycle has a composed two-minute stop/start budget, including native commands, status, process shutdown and readiness. Both the installer caller and native UI allow 125 seconds for that controller. Tests capture the actual subprocess context and preserve shorter caller cancellation. Payload installation and preflight select the recorded application location; renamed direct Applications bundles remain valid. Shared Applications is never chmodded, and a payload replacement that this account cannot complete is refused before service changes. Immutable root-owned bundles support explicit in-place setup only when their executable namespace is protected.

The startup executor uses that five-second native status budget even when its other requests use the longer explicit setup budget. Only the exact status argument form is a discardable read; Stop waiting cancels and reaps its private controller without interrupting an accepted mutation.

Shared-folder publication uses a separate bounded, no-follow descriptor writer. Production native copying preserves quarantine, ACLs, resource forks and extended attributes inside a private workspace, verifies the candidate, then moves it through checked directory descriptors. The generic private-state writer retains its stricter ancestor rules. Atomic shared-folder publication requires the home staging workspace and Applications to share a filesystem; a mismatch is refused during preflight before services stop. Actual system-folder writes remain a live qualification hold.

Execution requires protected ancestors. A group-writable shared Applications directory cannot retain custody of an executable name, even when an open directory descriptor and a valid signature are available. Such publication targets are refused before quiescence, and the Go and native execution paths reject the same unsafe namespace. Read-only package inspection retains its bounded shared-folder exception. The installer defaults to the account's Applications directory; it never changes system directory permissions to make a shared target pass. Root-owned sticky temporary ancestors outside the bundle retain their normal owner protection.

Publication pins the selected build before staging, verifies the candidate privately, then rechecks source, pending identity and installed target before activation. A private `publication-custody.json` receipt binds the app path and pending build to the exact candidate and optional backup device/inode, byte digest and build. An unrelated retained backup blocks even an identical reinstall before service changes. Recovery and cleanup require the same receipt and exact filesystem object; substituted entries and uncertain evidence remain intact. Failed staging removes only candidates and workspaces the installer still owns. Historical filename-only crash leftovers without a receipt are preserved for operator review rather than silently adopted.

Completing an interrupted payload publication through explicit in-place setup follows the same retained-custody validation and cleanup. It retires the exact owned backup and receipt before clearing the pending marker, so a successful retry cannot strand a record that blocks the next upgrade. A retained backup that cannot be cleaned with this account's permissions causes refusal before service changes. Immutable protected in-place setup without retained publication custody requires no app-bundle writes.

Phone access uses the same owning native interface. An ordinary enable is blocked while installation is pending or approval is revoked. The explicit installer migration reads the latest setting under the controller lock, and final installation publication holds that lock while verifying the current choice. It cannot re-register phone access from an earlier enabled snapshot.

## Installation channels and removal

The managed DMG presents the explicit installer. Historical self-installing drag images retain their verification path. Homebrew delivers the explicit installer and command links. The user opens the installer and chooses Install to install or upgrade the runtime. Homebrew upgrade or uninstall touches its delivery artifacts, leaving the independently installed runtime app and services in place. No install hook attempts native registration or queue IPC.

This channel decision follows installed Homebrew source evidence: its macOS sandbox denies outbound Unix sockets, general Mach service lookup, Launch Services opens and Apple events. Declaring network access does not authorize the private queue socket. Running lifecycle commands there cannot establish drain or readiness, and weakening the sandbox is outside scope. Homebrew's predecessor removal also happens before successor installation. Historical casks can delete a legacy menu plist while its job remains loaded; migration recognizes only the exact canonical loaded executable and arguments, rechecks custody and unregisters that known job. Arbitrary orphaned jobs remain refused.

Explicit `--prepare-replacement` and `--unregister-services` operations retain the same ownership and drain gates for callers outside that sandbox. Removal must return zero before deleting the runtime bundle. Data, history, configuration and credentials remain retained. Direct payload and app-bundle installation inspect generated CLI wrapper contents before any mutation, recheck under locks and recheck before publication. Custom scripts and symlinks are refused; exact historical Go and Python wrappers are supported.

A failed preparation or native shutdown blocks removal/replacement. Quitting the menu UI during ordinary operation does not unregister services. An incomplete marker is cleared only by successful explicit completion, not by ordinary startup or an optimistic cleanup command.

Replacement preparation refuses any unresolved publication receipt before service changes, because an external bundle move would invalidate the recorded candidate inode. Removal also refuses while that receipt retains a last-good backup; complete the exact pending setup first. A partial first installation with candidate-only custody can still unregister denied services: removal validates and retires its private receipt before clearing pending, leaving the app intact. The original denied-approval teardown regression remains unchanged and passes.

The private packaged acceptance test exposed a shutdown race after the review rounds: the scheduler could wait on the installer's retained scheduling lock while its signal handler was only observed after the current tick. A real child-process regression reproduced the ignored termination. The scheduler now owns a cancellation context, and its coordination-lock waits and queue RPC connection observe cancellation. The installer keeps its lock; stopping the helper does not require a forced kill or a larger timeout. The regression verifies that the lifetime lock is released and the installer's lock remains held. A private stalled-RPC test verifies connection closure and already-cancelled refusal.

The final fixture deliberately holds the private scheduling lock for the first removal attempt. It requires the existing busy diagnostic, an absent pending marker, unchanged installation identity and command wrappers, and an intact native-call witness with no mutation. It then releases the lock and permits at most three attempts within the unchanged operation deadline. Any accepted-mutation failure remains fatal. This exercises the product's existing safe refusal and explicit retry contract rather than assuming a background scheduler can never own the lock. Production locking was not relaxed.

Remaining acceptance boundaries:

- A release candidate needs the existing Developer ID, Apple notarization, stapling and both-architecture acceptance pipeline. Local ad hoc artifacts are development evidence.
- Real registration, approval denial/revocation, login, helper termination and upgrade/removal need an isolated macOS login session. The private fixtures test the controller and real queue with simulated native lifecycle operations; they do not isolate or exercise the workstation's actual Service Management registry.

Installation timing and native service packaging alone cannot establish that the original detection is resolved. No exclusion, scanner bypass or affected-machine retry is part of this implementation.
