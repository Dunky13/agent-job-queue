Inspect and correct workload learning

Use

Choose Learned workloads from the native app's gear menu or the phone dashboard navigation. Search by name, select a workload, and inspect its measured peaks, successful and incomplete run counts, variants and recent numeric measurements. A job's detail view links to its current learning profile.

The list opens on Projects, busiest first, each with its workload, group and run counts. Projects with two workloads or fewer share one Other projects row, and a note appears when more projects exist than the overview can list, saying how many are not shown; searching a project or group name finds them. Choose a project to see what it ran, one row per operation such as tests, build or lint with the same counts, plus All operations. Choose an operation to reach the group list, which has the selection checkboxes, group details and paging described below. In the phone dashboard a breadcrumb such as All projects / Sample app / Tests goes back to any earlier level; the native app has the same trail, with earlier parts as buttons, and a Back button. Search always covers every project, matching group names and the names of the projects behind them, and shows a flat list with groups whose own name matches before those that match only through a project; clear the box and search again to return to the level you were on. Returning from a group's details lands on the level and page it came from. Counts reload when you go back up a level or refresh, a project that a merge folded into Other projects still lists its groups and Back from them returns to the projects, a page past the end after a merge shows the last page, and a project or operation with nothing left shows an empty state with a way back.

Give a profile a useful name and save minimum RAM or CPU reservations when you know a job needs more headroom. Blank minimums return to automatic estimation. Sharing learning combines the original families under the selected target profile, keeping the larger reservations from both profiles. Separate a family when it should learn independently. Reset measurements only when the old evidence is obsolete; reset removes those measurements permanently while preserving your corrections.

Related workloads now share learning automatically within the same verified git repository, whatever subdirectory or linked worktree they ran in. Grouping needs a recognized tool (Go, JavaScript, Python, shell, Cargo, Swift or Make). Each workload also has an operation: tests, browser tests, native tests, race tests, full tests, build, lint, type check, dependencies, benchmark or combined checks, and other for mixed batches and anything unknown. Workloads with other share one group per repository and tool. Simple env and fnm exec wrappers, *.sh scripts and inline sh -c or bash -c programs are recognized for new jobs. Opaque scripts can use their safe task descriptions. Unrecognized tools and workloads outside a verified git repository remain independent. Project names alone never establish a repository match. Only the category is stored; command arguments and inline program text are never retained. A workload borrowing from its group always keeps its own measured peaks in full, in every variant. Each other workload in the group counts once, by its largest peak, and the highest tenth of those are set aside, so one runaway or unusually heavy workload cannot set the estimate for a large group. One in ten is set aside, so ten to nineteen other workloads set aside one and a group with fewer than ten still shares its largest peak. Nothing is averaged down. Groups an operator shared follow the same rule; save a minimum reservation on the group to hold every member above a figure.

Group estimates deliberately have no exact-variant successful-run count: they describe what a workload the group has not seen would borrow, so they can be lower than the group's largest measured peak, which is shown separately. Each actual job still has its own prediction and confidence. Measured history, the group estimate and operator minimums are displayed separately. Run history and variant peaks can include multiple machines; each run identifies its machine with an opaque hash, while the group estimate uses the current machine only.

The CLI has the same inspection and correction behavior:

agent-heavy profiles list --json
agent-heavy profiles list --query Tests --offset 0 --limit 100 --json
agent-heavy profiles list --project 'Agent Queue' --operation tests --json
agent-heavy profiles list --other-projects --json
agent-heavy profiles list --hierarchy --limit 50 --json

--project and --operation filter before paging; --other-projects selects the collapsed set described below and cannot be combined with --project. --hierarchy returns the project to operation overview and accepts only --limit. The authenticated HTTP equivalents are the project, operation, otherProjects=true and hierarchy=true query parameters on GET /api/profiles; invalid values are rejected.

Use the returned profile ID with agent-heavy profiles show ID --json. Edit, merge, split and reset take the profile ID and a JSON object on private standard input. Include the latest revision from the detail response. Edit requires label, memoryFloorBytes and cpuFloorCores, with null clearing a minimum. Merge requires targetId; split requires family; reset requires confirm: true. The response is the saved profile's new detail and revision. JSON failures contain an error message and exit with status 125.

An updated resource controller also performs one retroactive pass after its first successful collection. A failed pass is logged in the resource controller log and retried after ten minutes; it does not hold admissions, because history only improves grouping. Retained numeric runs are joined to private safe metadata without requiring original commands or surviving worktrees. A deleted checkout can still group when its old directory scope maps to exactly one live repository; a scope that maps to more than one repository stays unknown and independent. Every retained workload receives a stored classification, with other as the fallback. Missing metadata leaves a family independent. So does metadata that disagrees on a family's kind or verifies two different repositories, and later agreeing files cannot undo that; running in two subdirectories or worktrees of one repository is not a disagreement. Pinned profiles are never touched. The controller runs this backfill once, recorded as grouping version 2; an explicit profiles regroup --apply never marks it done. Running the command again is safe and can incorporate additional retained metadata. Known limit: the repository for a deleted checkout comes from the scope stored for its family, which is trusted. If an unrelated repository later reused that path, the family can be assigned the wrong repository; ungroup the workload to correct it.

Contract

The native app, phone dashboard and CLI expose learned workload profiles: their names, member job families, variants, successful and incomplete observations, measured resource peaks and recent runs. When a local machine identity is available, profile details also show the current resource prediction and its confidence. Unknown telemetry remains unavailable rather than inventing an estimate.

Job families remain independent of linked-worktree checkout paths and source revisions. A profile groups one or more families for statistical learning. Automatic groups combine compatible families; their job details identify the match as Automatic similar workloads. Operator corrections can rename a profile, share learning between profiles, separate a family into its own profile, set minimum CPU/RAM reservations, or reset obsolete measurements. Corrections pin those profiles so automatic grouping cannot undo them or add new members. A job's details link to the profile used for its prediction.

Sharing learning changes future lookup for existing and future variants of those families; it does not rewrite a command or merge exact-variant success counts. Machine-specific evidence stays machine-specific. Family transfer remains conservative until an exact variant has enough recent successful evidence. Separating a family restores its independent history because measurements retain their original family and variant identities.

Minimum reservations are explicit operator floors applied above the statistical estimate. They do not fabricate successful measurements or reduce observed peaks. Clearing a floor returns to the learned envelope. Resetting measurements is explicitly confirmed, preserves naming/grouping corrections and returns affected workloads to conservative cold-start learning. Active jobs continue and can contribute new measurements when they finish.

Consistency and privacy

Every mutation carries the revision the operator reviewed. Stale edits are rejected and require refresh. Changes invalidate pending automatic admission decisions and are applied by the independent controller on its next fresh pass. Existing active work and explicit manual overrides are preserved. A controller pass using predictions from before an edit cannot publish a new automatic grant afterward.

Adaptive corrections require a fresh acknowledgement from an updated controller. A still-running older controller and older waiting helpers cannot safely interpret the new grouping, so finish the installation and wait for its controller before editing in Adaptive mode, or deliberately select Fixed scheduling. Installation reloads only the resource controller before marking the upgrade complete. A failed reload leaves installation visibly incomplete and can be retried; the independent queue daemon keeps active jobs running.

The inspection API uses bounded summaries and numeric history. Names come from the existing safe job descriptions or explicit operator labels; raw arguments, inline programs, environment values and credentials are not retained by this feature. Read-only listing does not create or migrate a database. Private SQLite storage, bounded history, ownership checks and existing authenticated/CSRF browser boundaries remain in force.

Interface contract

The CLI entry point is agent-heavy profiles. List and show return JSON when requested. Changes use an explicit expected revision; reset additionally requires confirmation. The native and phone interfaces call the same CLI-owned behavior.

List responses contain revision, profiles, total, offset and limit. Each profile summary contains id, label, project, operation, memberCount, variantCount, successCount, incompleteCount, peakMemoryBytes, peakCpuCores, lastRunAt, memoryFloorBytes and cpuFloorCores. project is the most common member project, or Unknown project; operation is the shared operation, or other. An empty collection is a normal cold-start state.

The hierarchy response contains revision, projects, total and limit. Each project row has project, collapsed, workloadCount, groupCount, runCount and its operations, each with the same counts. Projects with two workloads or fewer collapse into one Other projects row with collapsed: true and a projectCount; filtering with --other-projects returns exactly the groups behind that row. At most 100 rows are returned in total, including the Other projects row, so limit counts it and total counts every project that is not collapsed.

Detail responses contain revision, profile, members, variants, runs, prediction, predictionMachine and truncated. A member contains family, label, project and executable. A variant contains id, family, successCount, incompleteCount, lastRunAt, peakMemoryBytes and peakCpuCores. A run contains id, family, variant, machine, sampledAt, memoryBytes, cpuCores, cpuSeconds, durationSeconds and success. Run records with success false are labelled incomplete or failed rather than being counted as successful evidence.

Prediction uses the existing memoryBytes, cpuCores, durationSeconds, samples, confidence and source fields, or null when machine identity is unavailable. predictionMachine is the opaque machine identifier or null. truncated contains boolean members, variants and runs flags where detail limits apply. All identities are opaque hashes; presentation does not claim that a hash is a reproducible-build cache key.

Catalog pages contain at most 100 profiles. A detail view contains at most 256 original families, 100 variants and 30 recent runs. Truncation is explicit and the same detail limits apply to the CLI. Bounded numeric retention can leave an upper envelope after individual run records expire; displayed successful and incomplete counts describe retained run records. Explicit naming and grouping corrections are pinned and never silently evicted to make room for automatic metadata.

Both response forms include controllerAppliedRevision and controllerStatus. Saving a correction can succeed before the controller acknowledges it; refresh learning to see that acknowledgement. Queue polling does not replace drafts or fetch profile history. Destructive confirmations bind to the reviewed profile and revision; a refresh cancels an old confirmation.
